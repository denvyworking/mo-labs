# План ЛР2 «Исследование механизмов распределения задач и координации»

## Что требует задание
Реализовать и экспериментально сравнить **не менее двух** механизмов распределения задач или координации
(централизованная диспетчеризация, контрактная сеть, аукцион, распределённое делегирование и др.).
Проанализировать показатели: время выполнения, число сообщений, стоимость координации и т.д.

## Механизмы (категория режима `allocation`)
1. `central` — централизованная диспетчеризация (уже есть в ядре, `lab1/mas/allocation.py`): диспетчер по
   телеметрии (возможно устаревшей) выбирает курьера с минимальным ожидаемым временем завершения.
2. `cnp` — **контрактная сеть** (FIPA Contract Net): диспетчер-менеджер объявляет CFP по заказу всем курьерам
   (заказ в статусе ANNOUNCED), курьеры-участники в течение окна отвечают PROPOSE (ставка = своя оценка
   `estimate()`, учитывающая очередь и заряд) или REFUSE; менеджер выбирает лучшее предложение — ACCEPT,
   остальным REJECT; победитель перепроверяет выполнимость и подтверждает (INFORM/AGREE) или сообщает FAILURE
   → повторное объявление. Рассмотреть проблему одновременных CFP (курьер выигрывает несколько контрактов,
   ставки которых считались без учёта друг друга): например, предварительные обязательства в ставках.
3. `auction` — **аукцион**: периодические раунды по пакету накопившихся заказов. Рекомендуемый вариант —
   последовательный аукцион по одному лоту (SSI): в каждом раунде курьеры подают ставки по всем лотам пакета
   (маргинальная стоимость с учётом уже выигранных), аукционист отдаёт один лот с наименьшей ставкой,
   ставки пересчитываются; цена победителя — по второй цене (Викри), для учёта дохода курьеров.
   Можно сравнить с параллельным одноразовым аукционом (дешевле по сообщениям, хуже по качеству).
4. (по возможности) `delegation` — **распределённое делегирование**: заказ получает один курьер (например,
   ближайший к точке выдачи по карте), а перегруженный курьер сам передаёт задачу соседу (одноранговый
   REQUEST/AGREE с ограничением числа передач). Полностью децентрализованная альтернатива.

Каждый механизм: плагин диспетчера + плагин участника для курьеров, явные сообщения через шину,
новые протоколы — в `roles.allow(...)`. Время работы алгоритма: `sim.metrics.timer("allocation")`.

## Эксперименты (одни и те же seed для всех механизмов — общие случайные числа)
- E1. Базовая конфигурация, 30 seed: все механизмы по всем показателям.
- E2. Масштабируемость: число курьеров 4, 8, 12, 16, 24 (поток заказов пропорционально) — рост сообщений
  и CPU координации против качества.
- E3. Нагрузка: интенсивность заказов 0.1, 0.2, 0.4, 0.8.
- E4. Задержка связи `msg_latency` 1, 2, 4 — устаревание информации (central) против раундов переговоров (cnp/auction).
- E5 (по желанию). Период телеметрии для central (5, 10, 20): цена «глобальной картины».

Показатели: `on_time_rate`, `urgent_on_time_rate`, `avg_delivery_time`, `p95_delivery_time`, `makespan`,
`avg_assign_latency`, `msgs_total`, `msgs_per_order`, сообщения на распределение отдельно от мониторинга
(`msgs_by_protocol`), `bytes_total`, `coord_cpu_ms`, `distance_total`, `energy_total`, `jain_tasks`,
`jain_earnings`, `utilization`, `reassignments`. Среднее ± 95% доверительный интервал.
